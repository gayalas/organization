===============================================================
POSTGRESQL 17 - CONTINUOUS PHYSICAL STREAMING REPLICATION
WINDOWS LAB MANUAL
===============================================================

PURPOSE
-------

This manual configures PostgreSQL 17 Physical Streaming Replication
on the same Windows machine.

Architecture:

    DB1 = PRIMARY
          READ / WRITE
          Port 5432

    DB2 = STANDBY
          READ ONLY
          Port 5433


                    WAL STREAMING
    +----------------------+        +----------------------+
    | DB1                  |        | DB2                  |
    | PostgreSQL 17        | -----> | PostgreSQL 17        |
    | Port: 5432           |        | Port: 5433           |
    | PRIMARY              |        | STANDBY              |
    | READ / WRITE         |        | READ ONLY             |
    +----------------------+        +----------------------+


IMPORTANT NOTES
---------------

1. DB1 is the PRIMARY server.

2. DB1 accepts:
       SELECT
       INSERT
       UPDATE
       DELETE
       CREATE
       ALTER
       DROP

3. DB2 is a physical STANDBY server.

4. DB2 can be queried with SELECT while it is in standby mode.

5. DB2 does NOT accept normal INSERT, UPDATE, DELETE or DDL operations
   while it is a physical standby.

6. Physical replication copies the entire PostgreSQL cluster.
   You do NOT create OrganizationDB manually on DB2.

7. DB2 receives WAL generated by DB1 and continuously replays it.

8. This LAB uses asynchronous replication:
       sync_state = async

9. DB2 is on the same Windows machine as DB1, but it is a separate
   PostgreSQL instance with a different data directory and port.

10. Never store a real production password in this manual.

11. This manual is for LAB/testing. Production replication requires
    additional security, monitoring, backups, failover procedures,
    networking and secret management.

===============================================================

    -D "C:\PostgreSQL-Lab\DB2" `
    -U postgres `

    --pwfile="C:\PostgreSQL-Lab\db2-password.txt"

After successful initialization, delete the temporary password file:

===============================================================
STEP 8 - CONFIGURE DB1 FOR REPLICATION
===============================================================

DB1 configuration file:

notepad "C:\Program Files\PostgreSQL\17\data\postgresql.conf"


Find:

    #wal_level = replica

Change to:

    wal_level = replica


Find:

    #max_wal_senders = 10

Change to:

    max_wal_senders = 10


Save the file.


WHY THESE SETTINGS?
-------------------

wal_level = replica

Tells PostgreSQL to generate the WAL information required for
physical streaming replication.


max_wal_senders = 10

Allows DB1 to create WAL sender processes for standby servers.


===============================================================
STEP 9 - CONFIGURE DB1 pg_hba.conf
===============================================================

Open:

notepad "C:\Program Files\PostgreSQL\17\data\pg_hba.conf"


Add this line if an equivalent rule does not already exist:

host    replication    replicator    127.0.0.1/32    scram-sha-256


Meaning:

    DB1
     |
     | replication connection
     |
     | user = replicator
     |
     | source = 127.0.0.1
     |
     v
    DB2


Because DB1 and DB2 are on the same Windows machine,
127.0.0.1 is used.


Save the file.

STEP 16 - RUN pg_basebackup
===============================================================

===============================================================
STEP 35 - IMPORTANT POSTGRESQL CONCEPTS
===============================================================


PRIMARY
-------

DB1 is the PRIMARY.

DB1 accepts:

    READ
    WRITE


STANDBY
-------

DB2 is the STANDBY.

DB2 accepts:

    READ

while it is in recovery mode.


---------------------------------------------------------------
PHYSICAL STREAMING REPLICATION
---------------------------------------------------------------

DB2 receives WAL generated by DB1.

DB2 replays those changes.

Because this is physical replication, the PostgreSQL cluster is
replicated rather than only one selected table.


---------------------------------------------------------------
WAL
---------------------------------------------------------------

WAL means:

    Write-Ahead Log


PostgreSQL writes transaction information to WAL.

The standby receives WAL and replays it.


---------------------------------------------------------------
ASYNCHRONOUS REPLICATION
---------------------------------------------------------------

This LAB uses:

    sync_state = async


DB1 does not wait for DB2 to confirm every transaction before
completing the transaction.

Therefore a small replication lag can exist.


---------------------------------------------------------------
REPLICATION LAG
---------------------------------------------------------------

DB1 and DB2 can temporarily be at slightly different positions.

For example:

    DB1:
        transaction completed

    DB2:
        transaction still being received/replayed


Usually the difference is small, but it depends on workload,
network and system performance.


---------------------------------------------------------------
FAILOVER
---------------------------------------------------------------

Replication and failover are different concepts.

Replication:

    DB1 ---> DB2


Failover:

    DB1 fails
       |
       v
    DB2 is promoted
       |
       v
    DB2 becomes PRIMARY


Promotion is a separate operational step.

A future LAB should cover:

    - detecting DB1 failure
    - checking replication state
    - promoting DB2
    - changing applications to DB2
    - validating the new primary
    - rebuilding the old DB1 as a standby
